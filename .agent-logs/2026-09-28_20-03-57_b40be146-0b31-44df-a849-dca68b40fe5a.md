## Higgsfield flow this is based on

- You pick a mode (Image or Video).
- You write a prompt in a composer docked at the bottom of the screen. Alongside it you set the model, aspect ratio, quality, number of outputs, a reference image, and for video a duration and a camera or motion preset.
- The cost shows on the Generate button.
- Placeholder cards appear in the results feed and fill in as each job finishes.
- Opening a result gives you actions such as reuse the prompt, animate an image into a video, and download.

**How we avoid a surface-level clone:** we'd make **iteration a first-class idea**.
- Every result remembers what it came from, for example "this video was animated from that image, which was a variant of this prompt".
- Results are grouped into **Projects**.
- Each result carries its full **recipe** (prompt, model and settings), which you can reload into the composer in one click.

## 1. Tech stack

| Area | Choice | Why |
|---|---|---|
| Framework | **Next.js 15 (App Router) + TypeScript** | Pages and mock API routes in one app, and deploys to Vercel with no setup |
| UI | **Tailwind + shadcn/ui (Radix)**, lucide icons | Accessible popovers, dialogs and sheets without building them ourselves |
| Motion | Framer Motion | Transitions for cards appearing, the viewer, and the mobile bottom sheet |
| State | **Zustand** with a persist layer | Small, and simple to persist |
| Storage | **IndexedDB** (`idb-keyval`) for uploaded reference images, localStorage for metadata | No backend database, and data survives a reload |
| Validation | Zod | Shared request and response types for the API |
| Tests | Vitest for the store and job lifecycle, plus one Playwright smoke test | Kept small to fit the time limit |

## 2. Pages

- **`/` Create:** the main workspace. Image/Video toggle, a results feed for the current project, and the docked composer.
- **`/library`:** every result across all projects, with filters for type, model, favorites and status, plus search.
- **`/projects`:** project cards with a cover image, count and last updated. **`/projects/[id]`** opens the Create workspace scoped to that project.
- **Asset viewer:** a full-screen overlay using Next's intercepting route (`/a/[id]`), so each result has its own link and closing it returns to the feed.

## 3. Core user flow

1. Pick or create a project; there's a default one.
2. Choose Image or Video, write a prompt, and optionally add a reference image or preset.
3. Adjust settings. The Generate button shows the cost.
4. Placeholder cards appear straight away with progress, and you can keep writing and queue more jobs.
5. Results fill in. Open one to see it large, favorite or download it, or "Use recipe", "Vary" or "Animate" (image to video).
6. The new job keeps a link to its parent, and the viewer shows that chain as a lineage strip.

## 5. State and data model

```
Project    { id, name, coverAssetId?, createdAt, updatedAt }
Generation { id, projectId, mode: 'image'|'video', prompt, modelId, presetId?,
             params: { aspectRatio, count, quality, durationSec?, seed },
             referenceAssetIds[], parentAssetId?,
             status: 'queued'|'running'|'succeeded'|'failed'|'canceled',
             progress, error?, cost, createdAt, completedAt? }
Asset      { id, generationId, projectId, kind: 'image'|'video'|'upload',
             url, thumbUrl, width, height, durationSec?, favorite, createdAt }
Model      { id, name, modes[], supportsReference, durations[], speed, costPerUnit }  // static list
Preset     { id, name, mode, category, promptHint, thumbUrl }                         // static list
UI         { activeProjectId, composerDraft, filters }
Credits    { balance }                                                                 // simulated
```

- **Stores:** Zustand slices for `projects`, `generations`, `assets`, `composer` and `credits`. Items are stored in flat maps by id, with selectors for each view.
- **Schema version:** the persisted data carries a version number so its format can change later.

## 6. How a generation runs

1. The composer checks the request (prompt present, model supports the mode, enough credits) and deducts credits right away.
2. `POST /api/generations` returns `{ jobId, etaMs }`. The client adds `Generation(status: queued)` to the store.
3. A `useJobPoller` hook calls `GET /api/generations/:jobId` about every 1s for each active job and updates progress.
4. When the job succeeds, the response includes its outputs. The client creates the `Asset` records and the card changes from placeholder to finished result.
5. On failure the credits are refunded and the card offers Retry, which reuses the same recipe. Cancel is available while a job is queued or running.

## 7. History and projects

- **Where results live:** every generation belongs to a project, and the Create feed shows that project's history, newest first.
- **Library:** shows all projects' results together, with filters.
- **Viewer actions:** from the viewer you can move a result to another project or make it the project cover.
- **"Use recipe":** reloads the composer with that result's prompt and settings.
- **Lineage:** it's followed through `parentAssetId`, and the viewer can show the chain in either direction.
- **Deleting a project:** asks first, then removes its generations and results.

## 8. Mock generation

- **Stateless timing:** the mock job id encodes the start time, parameters and seed. Progress is worked out from elapsed time, so it needs no server memory and works on Vercel's serverless functions.
- **Outputs:** chosen by seed from a **curated local set** (about 40 images in several aspect ratios and about 12 short muted MP4 loops). Picking by prompt keyword (portrait, landscape, product) makes results feel relevant.
- **Realism:** different models run at different speeds, about 5% of jobs fail at random (can be turned off), and results arrive one by one within a batch.
- **Swapping in a real provider later:** a `GenerationProvider` interface (`submit` / `status` / `cancel`) with `MockProvider` as the default. A real provider such as fal.ai or Replicate could be added behind an environment variable later, and the UI wouldn't change.

## 9. Responsive layout

- **Desktop (≥1024px):** a left nav rail, a masonry feed of 3–5 columns, and the composer as a floating bar at the bottom with settings in popovers.
- **Tablet:** the nav rail collapses to icons and the feed drops to 2–3 columns.
- **Mobile (<640px):**
  - A bottom tab bar, and the feed in 2 columns.
  - The composer shrinks to a one-line bar that opens a **bottom sheet** with all settings.
  - The viewer goes full screen with swipe navigation.
- **Everywhere:** a dark theme first, touch targets of at least 44px, safe-area padding, `prefers-reduced-motion` respected, lazy-loaded images, and videos that play on hover (desktop) or when scrolled into view (mobile).

## 10. What we won't build

- Sign-in, accounts, payments or real credit billing.
- Calls to real models. Only the adapter interface will exist.
- A backend database or cloud storage.
- A community or explore feed, public sharing, likes or comments.
- Editing tools: inpainting, canvas or masks, upscaling, a video timeline, or audio.
- Character or identity training (Higgsfield's "Soul ID").
- Collaboration or multiple users.
- Translations, analytics, a detailed settings page, or broad test coverage.
